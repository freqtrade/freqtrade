# 递归分析（Recursive analysis）

本页介绍如何验证你的策略是否由于某些指标的递归问题而存在不准确之处。

递归公式将序列的任何一项定义为其前一项（或多前项）的相对值。递归公式的一个例子是 a<sub>n</sub> = a<sub>n-1</sub> + b。

为什么这对 Freqtrade 很重要？在回测中，机器人将根据指定的 timerange 获取币对的完整数据。但在 dry/live 运行中，机器人将受到每个交易所提供的数据量的限制。

例如，要计算一个非常基础的指标 `steps`，第一行的价值始终为 0，而后续行的价值等于前一行的值加 1。如果我使用最新的 1000 根蜡烛来计算它，那么第一行的 `steps` 值为 0，而最后一根已收盘蜡烛处的 `steps` 值为 999。

如果计算只使用最新的 500 根蜡烛会怎样？那么最后一根已收盘蜡烛处的 `steps` 值就是 499，而不是 999。数值的差异意味着你的回测结果可能与你的 dry/live 运行结果不同。

`recursive-analysis` 命令需要有历史数据可用。要了解如何获取你感兴趣的币对和交易所的数据，
请前往文档的[数据下载](data-download.md)章节。

此命令基于准备不同长度的数据并基于它们计算指标而构建。
这不会回测策略本身，而只是计算指标。在不同起始蜡烛值（`startup_candle_count`）的指标计算完成后，比较所有指定 `startup_candle_count` 的最后一行数值，以查看它们与基准计算相比显示出多少方差。

命令设置：

- 使用 `-p` 选项设置你想要分析的币对。由于我们仅查看指标值，使用多个币对是多余的。最好使用价格相对较高且至少具有中等波动性的币对，例如 BTC 或 ETH，以避免可能使结果不准确的舍入问题。如果在命令上未设置币对，则此分析使用的币对是白名单中的第一个币对。
- 建议设置一个较长的 timerange（至少 5000 根蜡烛），以便将用作基准的初始指标计算本身具有非常小或没有递归问题。例如，对于 5m 时间周期，5000 根蜡烛的 timerange 将等于 18 天。
- `--cache` 被强制为 "none"，以避免自动加载先前的指标计算。

除了递归公式检查外，此命令还会对指标值本身进行一个简单的前瞻偏差检查。要进行完整的前瞻检查，请使用[前瞻分析（Lookahead-analysis）](lookahead-analysis.md)。

!!! Tip "通过 freqUI 运行 recursive-analysis"
    `recursive-analysis` 也可以通过 freqUI 运行，当 freqtrade 以 [webserver 模式](utils.md#webserver-模式) 运行时。
    由于分析可能会运行一段时间，它作为后台任务执行。

### 为什么使用奇数的默认起始蜡烛数？

起始蜡烛的默认值为奇数。当机器人从交易所的 API 获取蜡烛数据时，最后一根蜡烛是机器人正在检查的那根，其余数据是“起始蜡烛”。

例如，Binance 每次 API 调用允许 1000 根蜡烛。当机器人收到 1000 根蜡烛时，最后一根蜡烛是“当前蜡烛”，前面的 999 根蜡烛是“起始蜡烛”。通过将起始蜡烛数设置为 1000 而不是 999，机器人将尝试获取 1001 根蜡烛。然后交易所 API 将以分页形式发送蜡烛数据，即在 Binance API 的情况下，这将是两组——一组长度为 1000，另一组长度为 1。这导致机器人认为策略需要 1001 根蜡烛的数据，因此它将下载 2000 根蜡烛的数据，这意味着将有 1 根“当前蜡烛”和 1999 根“起始蜡烛”。

此外，交易所会限制连续批量 API 调用的次数，例如 Binance 允许 5 次调用。在这种情况下，在不触及 API 速率限制的情况下，只能从 Binance API 下载 5000 根蜡烛，这意味着你所能拥有的最大 `startup_candle_count` 为 4999。

请注意，交易所可能会在未事先通知的情况下更改此蜡烛限制。

### 命令如何工作？

- 首先使用提供的 timerange 进行初始指标计算，以生成指标值的基准。
- 设置基准后，它将针对每个不同的起始蜡烛计数值进行额外的运行。
- 然后，该命令将比较最后一根蜡烛行的指标值，并以表格形式报告差异。

## 理解 recursive-analysis 输出

这是一个输出结果表的示例，其中至少有一个指标存在递归公式问题：

```
| indicators   | 20      | 40      | 80     | 100    | 150     | 300     | 999    |
|--------------+---------+---------+--------+--------+---------+---------+--------|
| rsi_30       | nan%    | -6.025% | 0.612% | 0.828% | -0.140% | 0.000%  | 0.000% |
| rsi_14       | 24.141% | -0.876% | 0.070% | 0.007% | -0.000% | -0.000% | -      |
```

列标题表示分析中使用的不同 `startup_candle_count`。表中的值表示计算的指标值相对于基准值的方差。

`nan%` 意味着由于缺乏数据而无法计算该指标的值。在此示例中，你无法仅用 21 根蜡烛（1 根当前蜡烛 + 20 根起始蜡烛）计算长度为 30 的 RSI。

用户应针对每个指标评估该表，以确定指定的 `startup_candle_count` 是否会产生足够小的方差，从而使该指标不会对入场和/或出场产生任何影响。

因此，追求绝对零方差（由 `-` 值表示）可能并不是最佳选择，因为某些指标可能需要你使用如此长的 `startup_candle_count` 才能获得零方差。

## 注意事项

- `recursive-analysis` 只会计算并比较最后一行处的指标值。输出表报告不同起始蜡烛数计算与原始基准计算之间的百分比差异。它是否对你的入场和出场有任何实际影响并未包含。
- 理想的情况是，尽管起始蜡烛有所变化，指标将没有方差（或至少非常接近 0%）。实际上，像 EMA 这样的指标使用递归公式来计算指标值，因此目标不一定是要达到零百分比方差，而是要使方差足够低（因此 `startup_candle_count` 足够高），使得指标中固有的递归不会对交易决策产生任何实际影响。
- `recursive-analysis` 只会在 `populate_indicators` 和 `@informative` 装饰器上运行计算。如果你将任何指标计算放在 `populate_entry_trend` 或 `populate_exit_trend` 中，它将不会被计算。

## 通过 REST API 运行 recursive-analysis

`recursive-analysis` 也可以通过 REST API 触发，当 freqtrade 以 [webserver 模式](utils.md#webserver-模式) 运行时。
由于分析可能会运行一段时间，它作为后台任务执行。

1. `POST /api/v1/recursive_analysis`，请求体为 JSON，至少包含 `strategy` 和 `timerange`（可选：`timeframe`、`startup_candle`）。币对取自 webserver 配置。这将返回一个 `job_id`。
2. 轮询 `GET /api/v1/background/{job_id}` 以跟踪进度。
3. 完成后，通过 `GET /api/v1/recursive_analysis/{job_id}` 获取结果。

一次只能运行一个分析（前瞻分析或递归分析）。
